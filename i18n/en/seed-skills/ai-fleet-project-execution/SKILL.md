# AI Fleet Project Execution

## When to use

The user hands over a project with the instruction "take it through as a team, on your own". Triggers:
- "I'm leaving it to you, get it done"
- "Keep giving the agents tasks", 
- "I don't want to interfere, I only want the weekly report"

## KANBAN-FIRST workflow (MANDATORY default)

Every project and subtask MUST be managed through a kanban card. Ad-hoc delegation by inter-agent message only is for EMERGENCIES only (e.g. a broken-prod fix, time-critical pairing). Everything else:

1. **Subtask → new card**: with the project field, the assignee field (backend dev / marketing / video agent / etc.), priority + status='planned' or 'in_progress'.
2. **Delegation → inter-agent message + kanban reference**: refer to the card ID in the message (`See kanban card XXXX, status=in_progress`). The agent reports back on the card as well (writes a comment into the `kanban_comments` table).
3. **Sub-agent obligation**: built into the agent's CLAUDE.md, it MUST update the STATUS on every task (planned → in_progress → waiting/done). Not just an inter-agent reply.
4. **Orchestrator audit every 3-4 hours**: a scheduled task that, every 3 hours:
   - Cleans up done cards older than 7 days (archive)
   - Chases stuck tasks (>24h in_progress with no movement) with the assignee by inter-agent message
   - Flags new undelegated/unassigned cards to the orchestrator
5. **Weekly report**: the orchestrator summarizes the board state for the user on Telegram (every Friday).
6. **Meta-tasks do NOT go on the kanban**: anything that is a continuous monitor / scheduled task / permanent `/loop` cycle (e.g. "GitHub PR monitor", "Morning kickoff") must not be a kanban card, because the kanban audit will flag it as stuck. Keep these in a `~/.claude/scheduled-tasks/<name>/` folder or in `~/.claude/scheduled-tasks.json`. (Based on sub-agent feedback: PR watching is handled by its scheduled task, not by a kanban card.)

## Procedure

### 1. Kickoff (~30 min)

1. **Kanban parent card**: create one large hierarchy-tree parent card for the project. Description: scope, goals, rules.

2. **Sub-cards**: break the project into a per-agent sub-task list. Convention: `<projekt>m###` (orchestrator marketing coordination / DNS / weekly report), `<projekt>s###` (backend dev), `<projekt>n###` (urgent crash targets), etc. Every sub-card: assignee, priority, description, sort_order.

3. **Inter-agent kickoff**: send a detailed task list to the agents by inter-agent message. Separately for the marketing agent (business/marketing) and the backend dev agent (technical/development). Brief both sides, and warn them that there is NO auto-pull (they only work when you ping them).

4. **Weekly report scheduled task**: create `~/.claude/scheduled-tasks/<projekt>-weekly-report.md` with a cron-based report sender. Friday 17:00, kanban status + agent progress.

5. **HOT memory**: save the current state of the project (parent + sub-card IDs, scope, deadlines).

### 2. Ongoing coordination

- **Inter-agent msg = task delegation**, **kanban = state tracking**. Neither works without the other.
- **On every agent report**: 1) update the kanban card (status, comment), 2) inter-agent acknowledgement + next task, 3) Telegram update to the user ONLY if a decision is needed from them or it is an important milestone.
- **Parallel tasks**: if an agent has no blocked task, do NOT wait; give it a proactive "if you are bored" task (competitor analysis, README docs, etc.).
- **Brief revisions**: every review of yours must be concrete (a 1, 2, 3 point list of what to change). No general remarks ("I don't like it"); give concrete string replacements.

### 3. Handling stack pivots

The user often pivots the architecture based on an idea that comes up along the way. When reacting to pivots:

1. **Kanban update**: pivot info in a comment on the parent + affected sub-cards (what we switched to and why).
2. **Inter-agent msg**: re-brief the agents with the changed scope. Do NOT throw away work done BEFORE the pivot; port / reuse as much as possible (90% of the code usually survives).
3. **Decision log memory** (cold tier): record the pivots with timestamps.
4. **Time estimates**: do not estimate in human hours (the user explicitly corrected this). AI pace is ~5-10x faster than a human developer. 8 hours of work = 1 hour at AI-fleet pace.

### 4. Handling deploy blockers

The fleet cannot register Cloudflare/Netlify/Stripe accounts, because:
- computer-use Chrome tier=read (clicking blocked)
- There is usually no claude-in-chrome MCP
- Account creation is not supported through an API

So deploy blockers always wait on the user. Mitigation:
- **Bundle the requests into one Telegram msg** (CF token + Account ID + Netlify connect + DNS CNAME = one message; the user does it in 5-10 minutes).
- **Consider simplifying the stack**: if the architecture can be reduced to Supabase-only (Edge Functions = equivalent of a Worker proxy for an MVP), drop Cloudflare entirely. One vendor = one deploy blocker.

## Pitfalls

- **When delegating research, EXPLICITLY demand source labels and a recent time window.** By default the research sub-agent tends to build on older data points and give estimates for the current period. Fix: state it EXPLICITLY in the brief: 1) 'Focus on recent data: <concrete period>'. 2) 'A source label for every number: [FACT] vs [estimate] vs [NOT PUBLIC]. Estimate only when there really is no public data.' 3) When delegating HTML/presentations, have it distinguish the 3 categories visually with badges (green/amber/grey).

- **Video/asset render: a visual watch-check is mandatory before finalizing.** After a video render, do NOT settle for playing the mp4 once: use watch mode (live preview) or a frame-by-frame check at the critical moments (stagger peak, spring-back overshoot frame, animation peak). UI elements (card, chip, badge) must always stay within the layout bounds. When delegating, the brief contains: 'AFTER the render, check in watch mode or frame by frame that no UI element overflows the container bounds.'

- **When delegating to an asset-producing sub-agent, EXPLICITLY add 'send it on Telegram as an attachment'.** Asset-producing sub-agents tend to report only the file path back in an inter-agent message, and the user does NOT get the actual file. Correct brief rule: 'X done → send it to the user on Telegram (<user-chat-id>), attached with the reply tool's files: argument, with a short caption.' Always include it in the brief.

- **MCP disconnect: do your own reconnect with tmux send-keys.** The orchestrator runtime's tmux pane (check it with `tmux display-message -p '#S'`) is reachable with send-keys. Sequence: `tmux send-keys -t <orchestrator-session> "/mcp"` + Enter → wait 1-2s → arrow navigation (Up/Down) to the target server (the Telegram MCP is near the end of the list, in the Built-in MCPs section; check the `❯` cursor with capture-pane) → Enter (select) → Down → Enter (Reconnect). After 3s, capture-pane shows the success string "Reconnected to plugin:". **Do NOT use /mcp as a Skill tool or as a bot command**: it REALLY gets dismissed ("MCP dialog dismissed" log) and achieves nothing. (The feedback_mcp_reconnect memory details the 8-step procedure.)

- **Do not send a duplicate review**: if the sub-agent reports "same commit, already merged" / "it was a duplicate review", do NOT start another review agent. Compare the HEAD commit hash with the one already reviewed; if they match, stop. Fix: before a review run `gh pr view N --json headRefOid` and keep the already reviewed hashes in memory.

- **Auto-pull illusion**: the agents do NOT pull from the kanban. They only work when you ping them with an inter-agent msg. If you drop the thread for 30 minutes, everyone stops. The idea of a scheduled-task auto-ping produces a crowded msg stream (1 agent effectively does 1 task per iteration).

- **Estimating in human hours**: the user explicitly corrected this: "AI is not a human, it is much faster". Estimation ratio: 8 human hours = ~1 AI-fleet hour (in intensive focus). Not "1-2 days" but "2-3 focused hours". If you overestimate, the user will correct you.

- **Even more precise time bands by task size (calibration)**: 
  - **Micro task (a single-file refinement, a small parameter change, an SVG attribute swap)**: AI pace **1-3 minutes**. E.g. logo letterform iterations, 1-2 minutes each. Do not say 30-60 minutes, because the user corrects you ("I think it's much faster than that").
  - **Small task (rewriting one function, one compact PR)**: AI pace **5-15 minutes**.
  - **Medium task (a feature touching several files, writing a new connector from a template, adapting an MCP server)**: AI pace **30-90 minutes**.
  - **Large task (new architecture, stack pivot, full OAuth flow + Magic link UI)**: AI pace **2-4 hours** of intensive work.
  Use these bands for estimates, NOT extrapolation from human hours.

- **A stack pivot is never wasted work**: do not take the user's pivots as an insult. 90% of the earlier work can be ported (the code is architecture-independent, the encryption is WebCrypto-native, the OAuth handler is runtime-independent). Only the deploy target changes.

- **Computer-use Chrome tier=read**: you CANNOT register accounts on Cloudflare/Netlify/etc. automatically. Do not promise "I'll do it right away"; instead, cleanly delegate the 30-60 second UI flow to the user. Or, if the Claude-in-Chrome MCP is installed, try it through that.

- **Minimum Telegram noise**: do not send the user a Telegram message for every agent update. The weekly report + the moments that need a decision are enough. A review acknowledgement does NOT go to Telegram, only inter-agent.

- **Several agents racing**: if several agents would start on the same task, stop it with an explicit rule in CLAUDE.md. (E.g. the prior incident: one agent started an OAuth workaround flow that another agent also attempted.)

- **Child PR CLOSED+CONFLICTING after a PR squash merge**: if PRs are stacked (PR #1 on the feature/A branch, PR #2 on feature/B where B=A+commits), then AFTER PR #1 is squash-merged into main, the feature/A branch is automatically **deleted** (with the `--delete-branch` flag), which destroys the base of PR #2 -> CLOSED + CONFLICTING. The GitHub UI does not meaningfully support changing the base target in this situation. Fix: rebase the feature/B branch locally onto the updated main (`git rebase main`, which skips the duplicated commits as skipped cherry-picks), force-push under a new branch name, new PR with base=main.

- **gh pr create 504 timeout**: the GitHub GraphQL API sometimes returns a 504 Gateway Timeout. Simply retry after 3-5 seconds; it usually succeeds. Do not double-create: check with `gh pr list --repo X --state open` first whether it was already created.

- **Review rule for multi-PR delegation: the orchestrator reviews EVERY PR**: when a big feature splits into 5+ PRs and you delegated it to sub-agents, the user's explicit rule is: "ALWAYS do the reviews yourself". A sub-agent does not merge its own PR, no auto-merge, no "the user will review it" assumption. **Pattern**: (1) the sub-agent opens a PR, (2) pings inter-agent: "PR X ready for review: <url>", (3) the orchestrator runs `gh pr diff` + a local build/test, (4a) IF OK: the orchestrator merges + pings "merged, PR Y can start", (4b) IF a fix is needed: precise comment feedback (numbered issue list, marked "medium severity / critical"), the sub-agent fixes, pings again. The LOW-risk automatic merge rule that follows (below) REMAINS VALID for main-stream PRs (a single-author sub-agent's standalone bugfix), but in the case of MULTI-PR DELEGATION the orchestrator always reviews. Reason: the user's specific request for multi-PR features is that nothing slips through without review.
  - **A local tsc build is MANDATORY for orchestrator-repo PRs** (the prior incident): the backend dev agent's "tests PASS" claim can be MISLEADING. E.g. a channel-monitor generalization left a shorthand orphan reference in logger.info, which caused a `tsc` build failure during the daemon restart, AND THE PORT WENT DOWN, a dashboard outage of 5+ minutes. Sub-agent testing looks at the specific test file being green, but that is NOT a full build check. **Orchestrator rule**: for orchestrator-repo PRs ALWAYS run `npx tsc` yourself during review (NOT just the sub-agent's claim), BECAUSE if there is a bug in it and you merge it, the daemon falls over ON YOUR SIDE, and that causes an OUTAGE across the whole fleet orchestration. Plus: AFTER a PR merge, the explicit `npx tsc && launchctl kickstart -k gui/$(id -u)/com.<service>.dashboard` pattern (build + daemon restart). Do NOT kickstart ad hoc before the build, because the daemon runs from `dist/index.js` and a corrupt dist causes an outage.

- **Marveen SINGLE-INSTALL architecture clarification** (the user's explicit correction: "this is your machine! I don't have a machine!"): the Marveen model is ONE install, NOT client-server. The orchestrator install runs ON THE SANDBOX RUNTIME (orchestrator daemon + agents/* + dashboard). The user is a remote user and does NOT run a separate install: they talk to the orchestrator over TELEGRAM, and use the dashboard on the orchestrator host as well (localhost:3420 in their browser, tunnelled to the orchestrator sandbox runtime). **Pattern correction**: IF in the future you suggest machine configuration or an install operation to the user (commands like `cd ~/... && git pull`), that is a MISTAKE: the user has no CLI access and CANNOT run bash commands. Every install / build / daemon restart / git operation must happen on the orchestrator runtime (sandbox runtime), and the user experiences the result of the change in the dashboard / Telegram UI.

- **PR merge permission: judgment-based, NOT mandatory for every PR**: the user's explicit feedback was "if it's OK on your side, do the merge". A proactive merge is required if:
  - A sub-agent finished a PR, build OK
  - The diff is clear, low risk (UI bugfix, copy update, content tweak)
  - There is no irreversible effect (not a migration, not prod data, not a money flow)
  → MERGE AUTOMATICALLY, just send the user an update message that it is merged.
  
  ASK the user BEFORE merging if:
  - DB migration (irreversible schema change)
  - Production-affecting (money flow, user credits, encrypted credentials)
  - Architecture pivot (new feature scope, price change, branding)
  - Stack PR (several dependent PRs on top of each other, order-sensitive)
  - Uncertainty in the PR diff
  
  Reason: the over-cautious "I ask for permission on every PR" slows down fleet throughput. The user wants high-confidence routine UI/copy fixes to go through faster.
  
  How to apply: AFTER every PR create, do a quick mental risk check (low/medium/high). LOW = merge automatically + status update. MEDIUM/HIGH = ask. The EARLIER rule ("never chain it") STAYS for the `&&` bash command (because in a single tool call it is too fast, the user cannot step in), but a `gh pr create` + wait + `gh pr merge` separated down to the tool-call level is allowed for a LOW-risk PR.

- **MVP phasing proposal: ASK first, do not assume**: when proposing a new feature, do NOT assume that the user wants MVP-first / a phased rollout. Pattern: when proposing a new feature scope, calculate the plan with the full scope. If you want some feature later, ASK: "Should I start with an MVP (X tool first pass) or go straight to the full scope (X+Y all together)?" Do not decide the scope yourself (the user is revenue-focused and often likes full functionality in the first throw). How to apply: in a kanban plan for a new feature/connector/integration, the default assumption is full scope, and only propose an MVP if the concept is obviously too big.

- **A multi-line SQLite INSERT in a bash string is fragile**: `sqlite3 db "INSERT ... VALUES (..., 'multi-line description...')"` through a bash string tends to break on `'` and `"` escapes, a RETURNING clause, or a quoted description. Pattern: if there is a 2+ line INSERT or a long string, IMMEDIATELY use a temp .sql file + redirect, NOT a bash string. How to apply: when creating a kanban card, or for any SQL that also contains a description/long-text field, the default is the Write tool + .sql + sqlite3 redirect combo.

- **Hungarian accent loss in agent text**: if an agent (especially the backend dev agent, and sometimes other sonnet models) writes Hungarian string constants into code (e.g. translations.ts), it OFTEN strips the accents ("Hogyan mukodik" "Korai hozzaferes" etc.). This is not TUI encoding but ASCII-fying at the model output level. Mitigation: an explicit instruction in the inter-agent msg: "copy it WITH ACCENTS from the marketing agent's HU copy, do NOT write it in your own words". Verify: after the deploy, grep the output for typical accented words (`működik`, `hozzáférés`, `támogatás`, `hívás`, `Árak`, `Belépés`). If they are missing, a fix PR that rewrites the full translations. **Regression**: the backend dev agent STILL ASCII-fied, because I did not write an EXPLICIT `ÉKEZETESEN` ("with accents") warning into the inter-agent msg (I only pasted in the marketing agent's copy bullets). Pattern reinforcement: EVERY inter-agent msg that asks for a Hungarian UI/copy implementation MUST contain the `MINDEN MAGYAR SZÖVEG ÉKEZETESEN!` ("ALL HUNGARIAN TEXT WITH ACCENTS!") warning. **Third recurrence** (email templates: confirm-signup, magic-link, reset-password all ASCII-fied): the error EXTENDS to every Hungarian HTML/string asset (NOT only `translations.ts`-style i18n files), e.g. **email body HTML, marketing copy markdown, scheduled-task SKILL.md, system prompt templates, install-script echo lines**. **Pragmatic mitigation**: if the error is found in the post-merge, pre-apply phase, it is a two-way decision: either send the sub-agent back to fix it (slow, the cleaner path under the multi-PR review rule), OR fix it yourself with sed and force-push to the PR branch. Pragmatic choice: under 100 sed replacements you do it (faster, 5 minutes); over 100 replacements, or for a structural change, the sub-agent does.

- **Dashboard feature implementation: specify mock vs real data FIRST**: for a new dashboard page task, the sub-agent puts MOCK data into the UI by default. If real data is needed, specify it EXPLICITLY in the inter-agent msg:
  - "Data source: backend endpoint X (or create it if it does not exist yet)"
  - OR "mock is OK in the FIRST iteration, the real backend will be a separate kanban task"
  If the backend endpoint does not exist yet (analytics API etc.), THAT has to be delegated FIRST → BACKEND PR → the frontend can use it. Pattern: a dashboard feature task has 2 stages: (1) backend endpoint + schema, (2) frontend page + chart from the endpoint.

- **For a new dashboard page, always copy the existing auth-guard pattern**: new pages FIRST flashed the login screen AND after login redirected to the default page (did not stay on the original URL). Cause: the auth-guard logic and the redirect target were hardcoded. Fix: in the inter-agent msg, EXPLICITLY instruct the sub-agent to copy the existing auth pattern + use a post-login `?next=` parameter (current path).

- **Detecting Netlify production branch != main**: on the repo, the Netlify dashboard's Production branch setting CAN DRIFT from main to a feature branch. Symptom: you merge the PRs into main, and the dashboard does not show the fresh code. It can only be changed on the Netlify dashboard (Site config → Build & deploy → Continuous deployment → Branches), NOT in the repo's netlify.toml. Verify pattern: extract the MAIN sha with `gh api repos/.../commits/main -q .sha` + the Netlify deploy log "Preparing Git Reference refs/heads/<branch>"; if the two do not match, the user has to switch it.

- **Supabase onAuthStateChange SIGNED_OUT FALSE POSITIVE on page load**: the Supabase `onAuthStateChange` listener MAY FIRE a SIGNED_OUT event during page load even when the user is actually logged in (a session-recovery / token-refresh artifact). If code inside the Layout binds the SIGNED_OUT event to an automatic `window.location.href = '/login'`, this causes an infinite redirect loop or a "jumps back to the default page" bug. **Correct pattern**: the SIGNED_OUT event handler ONLY does localStorage cleanup, NO auto-redirect. The explicit logout button itself sends the redirect. OR: add a `?next=<window.location.pathname>` parameter to the SIGNED_OUT redirect too. Plus: for PRs touching auth/session/routing, TESTING (preview deploy + browser flow) is mandatory BEFORE you auto-merge.

- **Dashboard session token != backend API auth token mismatch**: the frontend authenticates with Supabase Auth (`supabase.auth.getSession().access_token`) and sends it as a Bearer token to the backend endpoints. BUT: the backend `authenticate()` function only accepted an api-key and an OAuth token; it did NOT know the Supabase JWT → 401 on every call → `apiFetch` redirect to `/login` (NO `?next=`) → /login falls back to the default page. **Correct fix pattern**: add Supabase JWT validation as a THIRD fallback to the backend `authenticate()` chain. The auth chain: `api_key → OAuth → Supabase JWT → null`. **Debug recipe**: if a dashboard page has a flash + redirect bug, FIRST CHECK the backend API responses on the network tab (status code, response body). If there are 401s → an AUTH mismatch between the frontend and the backend.

- **Bug-fix scope: if 2+ tools / endpoints fail on the same error pattern, fix them ALL at once**: e.g. in a connector, `query_transaction_list` and `query_invoice_digest` showed the same SOAP schema error. The first PR fixed only one of them, and at the next test the other one failed too → a second round trip. Pattern: in the bug report text, watch for the phrases "it does the same thing", "same error", "on every call" → these are SCOPE markers. Instruct EXPLICITLY in the inter-agent msg: "fix EVERY affected tool in one PR, NOT just the one that was named". Plus: if the error handling also needs a fix (validation message pass-through), apply it to EVERY tool, not just the current one.

- **Never assume logo asset integration**: if the video agent delivers brand SVGs into its own workspace, that does NOT mean the backend dev agent automatically lifts them into the frontend repo's `/public/` folder. It has to be told explicitly, or the orchestrator does it in a separate commit.

- **Verify a PID ENV leak diagnosis with `tmux list-panes -a`**: if unexpected ENV (e.g. another agent's STATE_DIR) shows up on an orchestrator-level PID in `ps eww`, do NOT assume right away that it leaked. First check with the output of `tmux list-panes -a -F "#{session_name} | #{pane_id} | #{pane_pid}"` which session pane the PID belongs to. Lesson: `tmux list-panes -a` takes 1 second and fits easily into the initial diagnosis.

- **Heartbeat-blocking IPC stall vs a real plugin disconnect**: the Telegram plugin "down" detection runs every minute. The 30-minute heartbeat scheduled task takes 60-90s to run, during which the Claude IPC is busy, and on a single tick the plugin looks `not alive` -> the dashboard starts the recovery flow (4 stages, 3-4 minutes of downtime). Mitigation: a 120s confirmation threshold: the first negative tick only records a suspicion, the second tick escalates. It filters out heartbeat stalls, and a real outage still triggers recovery within 2 minutes.

- **Claude Code TUI hourly MCP re-handshake (Anthropic side, NOT bug-fixable)**: the Claude Code TUI ITSELF automatically restarts the MCP stdio connections at every full hour (HH:00:00). The old connection closes cleanly after ~27-52s, and the new connection is handled in server.ts with the "stale poller replacement" pattern. This is an ARCHITECTURAL Claude Code feature; there is no CLI flag to turn it off. Mitigation pattern: (1) the soft reconnect with the Up-wraparound flow restores it automatically at Stage 1, (2) Stage-1 disconnect alerts in SILENT mode (no Telegram notification, only a warn log on the dashboard). Result: ~30-60s of downtime per hour, practically invisible in the UX. Stage 2+ alerts (memory save / session resume / hard restart) stay LIVE: those are the really serious cases.

- **Prompt design rule: the MANDATORY activity instruction goes FIRST, conditional silence SECOND**: if a prompt mandates an activity AND allows silence in certain cases, a CONTRADICTORY order is catastrophic. The heartbeat prompt put the no-op tool-call rule in the MIDDLE, AFTER the "Maradj csendben" ("Stay silent"): the orchestrator, as an LLM agent, chose silence, and I forgot the mandatory tool call. Telegram bun stdio idle → disconnect. **Pattern**: in prompt design, the MANDATORY-FIRST rule: when two instructions can be combined (mandatory activity + optional silence), the ACTIVITY instruction comes FIRST, the OPTION SECOND. Plus copy-pasteable examples > abstract description (an LLM agent looks for a pattern first). Own autonomy rule: in every task, FIRST do the low-level mandatory step, THEN think.

- **Telegram bun MCP stdio-stale-on-idle disconnect pattern**: if, because of an explicit "Maradj csendben" ("Stay silent") / "NE irj semmit" ("Do NOT write anything") instruction in the heartbeat prompt, the orchestrator agent does not call any MCP tool for 30+ minutes, the Telegram plugin's bun process detects its stdio pipe as stale and closes it. **Diagnostics**: (1) `ps aux | grep "bun.*telegram"` shows the parent claude processes; (2) the `.in_use/` session tracker files; (3) git log for changes to the schedule-runner heartbeat prompt. **Fix**: the heartbeat prompt REQUIRES the agent to CALL ONE no-op MCP tool on every heartbeat (Read/Bash echo), explicitly NOT a Telegram tool, so the user gets no noise. The no-op tool call generates a stdio flush, which keeps the Telegram bun pipe alive. **Follow-up**: the 30-minute heartbeat schedule + skipIfBusy=true sometimes produced a 16-21 minute gap, which hit the bun stdio stale threshold. Fix: schedule reduced from 30 min → 15 min. Pattern: the no-op tool call as a keep-alive only works if the max gap < the bun stdio stale timeout (~25-30 minutes); with a safe margin the interval has to be set to 15 min. **Differentiation lesson**: if the TIME of the drop falls between HH:00 and HH:05, it is NOT idle-stale (the heartbeat keep-alive does not help) but the hourly Claude Code TUI MCP re-handshake (a separate pattern, see above). Differentiate during diagnosis: (1) was the last keepalive in the keepalive log 25+ minutes earlier? → idle-stale, reduce the heartbeat interval; (2) drop between HH:00 and HH:05? → hourly re-handshake, a job for the soft reconnect. Do NOT jump to the heartbeat fix automatically for every disconnect: look at the keepalive log FIRST. **Regression diagnosis lesson**: if the user says "this was not a problem X days ago", ALWAYS run `git log --since="X+1 days ago" --oneline` first: the order of the recent telegram-monitor / heartbeat / schedule-runner PRs explains the regression after the fact. Pattern: measure every change that silences agents carefully for its side effect on the recovery flow. For silencing PRs a regression test is mandatory: measure the hourly disconnect recovery time over 24h. **/mcp picker viewport scroll pitfall**: a `tmux capture-pane`-based text search over the /mcp picker content is MISLEADING, because with 25+ MCPs the picker viewport scrolls and the target entry (Telegram) is NOT visible at the default top. Fix: the pre-check dropped, brute-force 1..MAX_UP_ATTEMPTS Up arrow + Enter + verify the "Plugin:telegram:telegram MCP Server" submenu header. On a match it continues to Reconnect; on a miss, Escape back to the picker and the next Up. Pattern: in TUI picker automation, do not rely on pane text search if the list can scroll; a verify step + per-attempt iteration is more reliable. AND: the "Up wraparound" fixed assumption (Telegram=last entry) breaks after ANY new MCP, so brute force is the more robust default than fixed-N navigation. **Validation**: matchedAt=1 in every cycle → recovery <10s. CRITICAL LESSON: `claude mcp list` ≠ the /mcp picker order. Pattern: TUI picker order != CLI list order; do not deduce the picker position from CLI output, use a brute-force verify loop.

- **Sub-agent API 500 (Anthropic server error) recovery workflow** (the prior incident, a backend dev agent task): the sub-agent gets stuck with an "API Error: 500 Internal server error" message. The token count suddenly drops, but the TUI is still running and many background shells are active. The fault is NOT on our side; it is on Anthropic's server side (confirm on status.claude.com). **User-validated recovery workflow pattern**:
  1. **Esc Esc** into the sub-agent pane → interrupt the current task
  2. **`/compact` + Enter** → compress the conversation history (context refresh)
  3. **Wait 1 hour** (Anthropic incidents are typically resolved within 15-60 minutes)
  4. **`WebFetch status.claude.com`** → whether the "Elevated error rates" incident is already resolved
  5. **Restart** the sub-agent task with an inter-agent message
  
  **NOT "postpone to tomorrow"**: the user's explicit pattern is to retry the same day after 1 hour, not the next day. **TODO in memory, hot tier**: a concrete time + action, tracked between heartbeats.

- **"Request interrupted by user" near a heartbeat window ≠ an intentional user interrupt**: if a Bash command or a longer tool sequence stops with a "Request interrupted by user" message, and this happens close to a heartbeat window (the system reminders come in), do NOT assume that the user intervened on purpose. It may be a quirk of the Bash tool's background process, or a limitation of the system reminders frame. **Check pattern**: before treating such a signal as a "user interrupt", think it through: (1) is there a quotable Telegram message containing a user reply? (2) an actual escape/cancel action on the tool dialog? If the answer to both is NO, it is a heartbeat quirk; retry the command.

- **Sub-agent stuck shell + "1 shell still running" TUI block**: the sub-agent's Claude Code TUI blocks new user input if the "1 shell still running" indicator persists: an earlier background shell did NOT finish, ever. **Diagnostics**: (1) `tmux list-panes -t agent-<name> -F '#{pane_pid}'` → you get a PID (claude.exe), (2) `pgrep -P <pid>` → list of child processes, (3) `ps -o pid,etime,command -p <PID>...` → the zsh shell child with a long ETIME is the culprit. **Fix**: `kill <stuck_shell_pid>`. **Sub-agent restart via the dashboard API**:
1. `tmux kill-session -t agent-<name>` (kills the stuck session)
2. `curl -s -X POST http://localhost:3420/api/agents/<name>/start -H "Authorization: Bearer $(cat store/.dashboard-token)"` → `{"ok":true}` response
3. Verify: `tmux ls | grep agent-<name>` → a new session with a fresh "created" date
4. `ps -o pid,etime,command -p <pid>` → `claude --continue --dangerously-skip-permissions --model <model> --channels plugin:telegram@claude-plugins-official` is running; "continue" mode loads the last session state
5. Verify ping: an inter-agent message on `/api/messages`, wait for the reply within ~30-60s

- **Privacy architecture B vs C trade-off (encryption)**: B (Platform Vault, server-side encryption + master_key in the vault) has a fast UX (1 api-key in the Claude config), BUT from a marketing point of view the "your data never reaches us" claim is INACCURATE. ## Pitfall: the shape contract in parallel backend+frontend delegation

**Problem**: two agents (backend dev + marketing/frontend) worked in parallel on a new feature (an admin page with aggregate stats endpoints and a chart). The backend dev wrote the RPC response in the `{ts: ISO, calls: number}[]` shape, the frontend expected `{label: string, count: number}[]`. Result: an empty chart (every field `undefined`); the user reported it with a screenshot. A separate PR was needed for the mapping.

**Fix**: when backend + frontend go in parallel to two different agents, the orchestrator-coordinator delegation prompt must give an EXPLICIT JSON shape contract to BOTH sides. E.g.:

> Backend response shape: `{ts: ISO-8601 string, calls: integer}[]`. The frontend accepts EXACTLY this shape, do not map it to something else; if the renderer expects different field names, the renderer must be adapted to the shape defined in the backend, not the other way round.

As a pattern: the last paragraph of the orchestrator prompt has a "**Wire contract** (both agents must use this):" section, and lists the key endpoints + their JSON shapes. Written once, it takes 30 sec and saves 1-2 fix PRs.

## Pitfall: hardcoded Chart.js colors on a light theme

**Problem**: the chart config tick + grid colors were hardcoded `rgba(255,255,255,0.3-0.5)`, designed for a dark theme. But the user opened it on the light theme, and the labels were invisible.

**Fix**: every Chart.js `ticks.color`, `grid.color`, `tooltip.bodyColor` value must be CSS-var-driven, at runtime with the expression `getComputedStyle(document.documentElement).getPropertyValue('--ink-2').trim()`. Typical variable mapping: `--ink-2` → tick color, `--border` → grid color, `--accent` → primary fill/stroke. A fallback dark-themed value, but the runtime value always wins.

Snippet:
```ts
const css = (name: string, fb: string) => getComputedStyle(document.documentElement).getPropertyValue(name).trim() || fb;
const tickColor = css('--ink-2', 'rgba(0,0,0,0.55)');
const gridColor = css('--border', 'rgba(0,0,0,0.08)');
```

**In the delegation prompt to the frontend agent**: when you ask for chart rendering, write EXPLICITLY: "tick + grid colors CSS-var-driven (`--ink-2`, `--border`), NOT hardcoded".
