# Kanban audit: pitfalls (references)

- **Your own commenting hides the card from the age-based metrics.** A
  comment (and every card write) refreshes `updated_at`, so the
  `waiting > 48h` list can turn EMPTY just because you yourself wrote on the
  card in the previous round. 2026-08-11, own measurement: a card had been waiting for 307 hours, I
  commented on it at 12:00, and at the 16:00 audit `waiting > 48h` was already 0 -- not
  because it was resolved, but because I touched it. The direction of the error is
  reassuring, and that is what makes it dangerous: a silent zero that looks like success.
  If you measure "0 blockers", check whether the card moved since the previous audit AND who
  moved it:
  ```bash
  python3 -c "
  import sqlite3
  c=sqlite3.connect('store/claudeclaw.db')
  r=c.execute(\"select author from kanban_comments where card_id=? order by created_at desc limit 1\", ('<id>',)).fetchone()
  print(r[0] if r else '(no comment)')"
  ```
  `updated_at` is the time of the last WRITE, not of the last real movement of the work.
  **Compare the REAL age against `created_at` if the `updated_at` is your own write.**
  2026-08-25: a card measured as 162.5 hours old, but its `updated_at` was my own comment from a
  week earlier; the card had been created 14 days before. A twofold difference
  decides whether it can wait one more day, so in the report state the real age,
  together with the measured one.
  This implies a restraint too: **do not comment on the card merely to
  record that you looked at it.** If you only checked, say so on the channel, not on the
  board. Write a comment when you MEASURED something that stays relevant on the card.
- **Do NOT use the `sqlite3` CLI and do NOT use `jq`.** Neither is installed on an average Linux
  machine (the installer's dependencies: ffmpeg, git, tmux, lsof, curl, python3, pipx, unzip), and the
  call dies there with `exit 127` -- this step is silently skipped while the audit looks
  successful. Measured on a live machine 2026-08-04: on two separate Linux installs `sqlite3` and `jq`
  were both missing, `python3` was present on both. It went unnoticed on the macOS machines
  because `sqlite3` ships there by default.
- **DO NOT HIT THE 300 CHARACTER TITLE GATE, AND IF YOU DO, DO NOT DELETE THE TRACE (2026-08-26, own measurement in the Dream Engine).**
  The `kanban_cards_title_gate_*` trigger cuts the title above 300 and puts the full text into a
  `cim-kapu (trigger)` comment. **In a single evening session I ran into it SEVEN TIMES** (MIOAGENTSZO825,
  INSTPWURES825 twice, INSTROOTDESKTOP825, MACHW825, DIGESTSTALE825, MIOPIN825), and every time the fix
  was the same: rewrite it shorter.
  **THE PRIMARY FIX IS THE EDITING HABIT, NOT THE REPAIR:** the TITLE should be one line (finding + owner + deadline),
  and write the long description into a comment FROM THE START, yourself. That way the trigger never fires.
  **AND THE MEASUREMENT TRAP, WHICH IS THE MOST VALUABLE PART:** of the seven, ONLY TWO are measurable TODAY, because
  after fixing the title I deleted the trigger's own comment every time. The cleanup erased the signal
  from which a later round could measure that this is a recurring problem -- the `length(title)=300` fingerprint
  also disappears as soon as you fix the title. **If the trigger fired, do not delete its comment silently:** either leave
  it, or replace it with ONE line saying when and on which card it fired.
  **THE GENERAL RULE: if an automation leaves a TRACE of its own operation, do not delete that trace
  in the same round in which we fix the error** -- otherwise after every individual fix it looks as if
  the problem did not exist. The same family as when the evidence gets into the index and blinds the
  detector.

- **A `waiting` CARD IS NOT PROOF THAT THE BUG STILL EXISTS -- live code, not card text (2026-07-25, 5F996CBC, own error)**: the "Dashboard vault-save UI does not check res.ok -> silent false success" card sat on `waiting`, I took this as fact, escalated it as a blocker (priority high) and ASKED THE OWNER to hold off on entering the credential. The fix had actually gone in **a month earlier** (af48837 / PR #430, 06-21) and was on develop; the vault-add branch of `web/app.js` has the `res.ok` check + error toast. Nobody closed the card, so it stayed "alive". PROCEDURE before you escalate a card as a blocker or hold the owner back with it: (1) `git log --oneline --all -S"<a hibás minta>"` or `grep` in the LIVE file, (2) `git branch --contains <fix-sha>` to see whether it is on the deployed branch, (3) only then escalate. If it turns out to be stale: close the card AND correct yourself with the owner, saying explicitly that you held them back on wrong info. This belongs to the same family as the premise going stale on PR cards (see `pr-auto-process` Pitfalls).
- The condition "has not moved since the previous audit" means: `updated_at < last_audit_at`. Do NOT use an absolute 24h threshold.
- Do not archive done if <7 days (the owner still wants to see it). **EXCEPTION: on an explicit "review and clean up" / "clean up the kanban" owner request, archive ALL done cards (the explicit request overrides the <7 day standing default, 2026-06-17).**
- **DEEP-CLEAN ("clean up") extra steps beyond the plain archive (2026-06-17)**: (1) for waiting/planned PR cards verify the actual state of the PR (`gh pr view <n> --json state,mergedAt`) -- cards of MERGED/CLOSED PRs are to be set to done and archived (e.g. #368 merged, #351 closed stayed on waiting/planned). (2) DEDUP by TOPIC, NOT only by PR number: for the same work there is often ONE task card AND one PR card (e.g. frontend tax validation task vs aiam #73 PR), or two agents card the same thing (e.g. the 015-hardening B6E4CB76 [me] vs 876ec002 [Samu PR] -- the pr-auto-process PR-number dedup does NOT catch this). Archive the duplicate, keep the canonical tracker. (3) Do NOT close legit open backlog (Samu tech-debt/repro queue, roadmap, decision-backlog) -- the deep-clean is done+obsolete+duplicate, not backlog pruning; that is done SEPARATELY, in agreement with the owner.
- **THIRD DUPLICATE FORM: two agents react to THE SAME FRESH observation, within minutes (2026-07-29, own error)**: the dedup rule so far covered the "topic vs PR number" and the "two agents card the same OLD work" cases. The third is faster and sneakier: I sent an observation to the developer saying "add it to a low-prio card", and MEANWHILE I added one too -- two cards, the same work, within minutes. The dedup check does not help here, because the other card did not exist yet at the moment of the query. **The prevention is in the wording, not in a query: if I add it, I SAY SO ("added it as X, nothing for you to do") and I do NOT ask the other one to do the same; if they should add it, I do NOT add it.** If it happened anyway: the EXECUTOR's card becomes the canonical one (that is what they will work from), archive the other, carry the reasoning over as a comment, and say whose error it was.
  **THE SAME THING HAPPENED AGAIN WITHIN AN HOUR (2026-07-29, BRIDGENET1) -- so it is not carelessness but a missing step in the process.** The second case looked exactly like the first: at the end of the message I asked the developer to "add it to a card", and then in the same round I added it myself. **THE MECHANISM THAT CATCHES IT: decide the card owner BEFORE you write the message, not at the end -- and a single message must NEVER contain both "added it" and "add it".** If a card comes out of an observation, the sentence is either one or the other; there is no third option. After writing, before sending: grep your own text for both phrases.

  **IT HAPPENED A THIRD TIME (2026-08-04, in two pairs at once: MIGGATE804/UPDMAINTGATE804 and UPDSTASH804/UPDCONFL804) -- and that is when it turned out that the gap is TWO-SIDED.** After the previous two cases the rule and the check next to it were written down; the error still repeated, because I did not run the written grep. The same message contained "open a separate card" and -- a few minutes later, in the same round -- my own card.
  **WHAT IS NEW, AND WHY FIXING YOUR OWN SIDE IS NOT ENOUGH:** the executor also opens a card for their own finding, and they do not search for existing ones either. That day they opened three cards and not once ran a title search before. So the duplicate is born even if MY message is clean -- the two sides card the same finding independently of each other.
  **THE TWO-SIDED MECHANISM we agreed on:** (1) on my side the pre-send grep on my own text, actually run, not just written down; (2) on the executor's side, before opening a card, a grep on the TITLES of non-archived cards with the keywords of the finding (not on their own wording -- see `feedback_search_the_concept_not_the_sentence`), and on a hit a comment on the existing card, not a new card.
  **RESOLUTION, if it happened anyway:** the EXECUTOR's card is the canonical one (they work from it), mine is to be archived with its content carried over -- and in the resolution say on which side the error arose. Here on both.

- **THE DEDUP CHECK IS NEEDED NOT ONLY BEFORE CARDING BUT ALSO BEFORE DELEGATING (2026-07-29, own error, expensive)**: so far the rule applied to card creation. That day I started a half-day investigation for two agents from a customer report -- and at the end it turned out that **a `planned` card about this same bug had been sitting for three weeks**, which already described the main mechanism, and in one of its comments even the second one. Most of the work was rediscovery. I ran the card search AFTER the work, not before. **PROCEDURE: before you HAND OUT any investigation or fix, search the board for the topic** -- not only by ID, but by subject word and system name (`title LIKE '%<rendszer>%' OR title LIKE '%<tunet>%'`), and look at the `planned` ones too, not only the active ones. If there is a hit, that should be the canonical card, and in the brief TELL the agent to start from there.
  **WHAT STILL WAS NOT WASTED IN SUCH A CASE, and say this too:** the old card typically records a HYPOTHESIS; the new measurement turns it into EVIDENCE, and often brings a branch that is not in the old one. The two together are worth more than separately -- but the reverse order would have been cheaper.

- **Dedup check BEFORE card creation (duplicate prevention)**: before you create a task card for delegated work, check whether there is already a card for the same thing (topic + PR number), otherwise a duplicate is created (like the 015-hardening above).
- Do NOT ping yourself (skip if the assignee is the main agent ({{MAIN_AGENT_ID}})). **BUT THE SKIP DOES NOT MEAN YOU PASS OVER IT -- this is a structural blind spot (2026-07-28, own case).** The ping mechanism watches every agent, with ONE exception: me. If my own card gets stuck, there is nobody to say so, so it keeps sitting quietly, even for weeks. Concretely: my `connectors.hu MVP` card had been on `in_progress` for 28 hours, although that day we worked on other things the whole time -- the board claimed that someone was working on it right now. **PROCEDURE: for stuck cards with the main agent as assignee, instead of the ping I DECIDE MYSELF in the same round** -- either I continue (and comment where it stands), or I set it to `waiting` with the reason. Skipping the ping is correct; skipping the decision is not. The same principle as in point 5 of the delegation watcher: `in_progress` claims that someone is working on it RIGHT NOW -- if nobody is, the board is lying.
- **THE ZERO MEASUREMENT IS THE FASTEST-AGING CLAIM ON A CARD -- and nothing signals when it goes stale (2026-08-04, GOOGLEVERIF1 + A475A648)**: two of our cards recorded that the Google connector has **zero external connections**, and that the connector is **dormant** and waiting for the owner's decision. Both were TRUE at the 07-27 measurement. The mandatory opening measurement of the daily connectors round, however, showed that since 08-02 an external person has been actively calling it, today too, including Gmail sending, with zero errors. Nobody was wrong; the claim **went bad by itself**, because a single new user reverses it, and no signal arrives about that.
  **WHY A SEPARATE CLASS:** a "there are many of it" claim moves slowly, a **"there are zero of it" claim falls with a single one**. And it is exactly the zero claims that carry the strongest conclusions ("there is no demand for it", "no need to deal with it", "waiting for the owner"), so it is the most expensive when it goes stale silently.
  **PROCEDURE:** if a card records a zero measurement, the text should include the DATE OF THE MEASUREMENT and WHAT decides it again (which query, on which table). When you touch such a card, run the measurement again, do not read the text -- this takes a few seconds, and it protects exactly the conclusion we build on most. The same family as "the card's premise goes stale", only here the direction of failure is fixed: zero can always move UPWARD, and it never signals.

- **The 30+ day waiting list is not only debt but a SOURCE OF KNOWLEDGE (2026-07-28)**: the real benefit of that day's audit was a by-product. `3BB2E738` (WSL2 install, "Windows-claude-WSL trap") had sat untouched for 53 days -- and became relevant that evening, because the owner was just asking for the Windows/WSL branch. Handed to the developer, it saved a rediscovery. **So do not look at the list only as a number: skim the TITLES through the lens of the day's active topics, and if one of them is input to work running now, hand it to whoever is working on it.** An old card is not necessarily dead -- it may just have arrived early.
  **BUT: TOPICAL CLOSENESS IS NOT INPUT (2026-07-31, the other edge of the same rule).** `AFBDE2AD` (#470 delivery-intent gate, security) had sat for 33 days, and that day the developer was WORKING on gate security (#770 Bash auto-approve + a fresh bypass card). It would have been obvious to hand it over "as context". I did not: that is a **different gate**, a related family, but not input to the running round -- and that day the P0 was observing a 10:00 customer install. Handing over adjacent material on a P0 day is not a service but a cost.
  **THE DISTINCTION:** input is what the running work draws from NOW (the same file, the same gate, the same error symptom, data already measured). Adjacent is what falls under the same TOPIC. If you are unsure: is it input enough that the other person would stop what they are doing NOW because of it? If not, it is not input.
  **WHAT TO DO INSTEAD FOR ADJACENCY:** do not hand it to the person, write the pattern onto the CARD. That day this came out of it: three open gate-security threads at once (33-day conflicting draft, running review, fresh bypass finding), and all three are about the same thing -- what an automatic gate lets through. **This is not raising urgency: it becomes useful because at the next priority weighing there is already a pattern there, not three separate items.** (Related: the "strengthen the evidence without escalating" point below.)
  **AND BEFORE THAT, MEASURE THE LIVE STATE:** instead of the 33-day card text, `gh pr view` -- it turned out that the PR had become CONFLICTING in the meantime. The card was not stale, the situation had got worse; without this I would have written "unchanged".

  **`gh pr view`, HOWEVER, DOES NOT TELL YOU WHETHER IT SHIPPED -- that needs a separate measurement (2026-08-01, 20d70901)**: the card claimed that three fixes were "waiting on develop, the develop->main release is still to come". `gh pr view` gave `MERGED` for all three, which only means that they went into *develop* -- this neither confirms nor refutes the card's claim. ONE command answers the shipping question: `gh api "repos/<o>/<r>/compare/main...<merge-sha>" -q .status` -> **`behind` = main ALREADY contains it (shipped), `ahead`/`diverged` = not yet**. All three fixes were `behind`, live since 2026-06-29; so the release part of the card had been a dead premise for weeks, while its HOST-VERIFY part really did stay open. **PROCEDURE: if an old card claims "waiting for release", the merge state is NOT enough evidence -- `compare/main...<sha>` is the measurement.** And if the card has gone partly stale, fix the title too, not only the body (see `feedback_merged_is_not_live_for_security_fix`).

- **AN OLD RISK CARD CAN BE STRENGTHENED WITHOUT ESCALATING IT (2026-07-29)**: `56dd56bf` (fleet-wide Supabase prod-write lockdown) has been waiting for 36 days, and yesterday I correctly did NOT escalate it, because according to the live state the technical lock is done, only moving the vault PAT remained. The temptation in such a case is to write the same thing again in the next audit ("unchanged"), and the card slowly turns into background noise. **What to do instead: look for whether something happened THAT DAY that makes the card's risk MORE CONCRETE.** That day, in three separate tasks, I used the same shared `MARVEEN-CONNECTORS-PAT`, on two Supabase projects as well that have nothing to do with the day's work -- meaning that "a Management API key with full DDL/DML rights sits in a shared place" is not a theoretical but a DAILY-USE exposure. This is not raising urgency and not escalation: a comment that will be a fact at the next priority weighing, not a feeling. **Principle: while the `waiting` status is kept, the EVIDENCE can get stronger -- and this is exactly what separates a live risk register from a graveyard.**
  **BUT STRENGTHENING THE EVIDENCE ALSO HAS A SATURATION POINT (2026-08-04, 5E0A32B0, the 20:00 audit)**: the rule above encourages you to measure and comment on the old card. That day this 63-day calendar-auth card was re-measured by the 08:00, the 12:00 AND the 16:00 audit, all three also commented on it, and in the 20:00 round there was the urge for a fourth -- with the same content ("the heartbeat calendar section is broken today too"). Such a fourth comment no longer strengthens the evidence, it only makes the card longer, and it achieves exactly the effect the rule was born against: the card turns into background noise, only this time from my own comments.
  **PROCEDURE: before you write evidence onto an old card, look at its comments FROM TODAY** (`SELECT date(created_at,'unixepoch','localtime'), substr(content,1,120) FROM kanban_comments WHERE card_id='<id>' ORDER BY created_at DESC LIMIT 3`). If the same measurement is already there today, the right step is silence. A new comment only if the RESULT of the measurement changed (the symptom disappeared, got worse, or traces back to a different cause), not if you just ran it again.
- Do not re-ping the same thing within 4 hours: the `last_audit_at` stored in the state file handles this automatically (see step 1, for the first run too).
- A status change (in_progress -> done) also means an updated_at refresh, so the next audit will not catch the tasks that are still active right now.
- **Do NOT rewrite the stuck measurement with your own SQL** (the old query, `in_progress` only, was structurally empty): activity (the assignee's comment, event, edit) lives in `/api/kanban/stuck`, step 3 calls that.

- **`changes()` in a SEPARATE sqlite3 call is ALWAYS 0 (2026-06-15)**: if after the UPDATE `sqlite3 ... "SELECT changes()"` runs in a separate invocation, that is a NEW connection -> it gives 0 even if the UPDATE succeeded (false negative, "0 rows modified" appearance). Do NOT rely on this. Verify the effect with a count before/after (e.g. unassigned count 11->5), or put the `SELECT changes();` in THE SAME sqlite3 call after the UPDATE (`sqlite3 db "UPDATE ...; SELECT changes();"`).
- **Batch UPDATE with a `{ ... } | sqlite3` subshell pipe + loop-built `$SQL` string can SILENTLY roll back (2026-07-20)**: when closing many cards at once, the `for id in ...; do SQL="$SQL UPDATE...;INSERT..."; done; sqlite3 db "$SQL ..."` pattern silently modified 0 rows (the closing SELECT ran and gave a normal number, but NOTHING was written -- probably one statement in the loop-built string broke the parse, with no error message in the capture). RELIABLE PATTERN: (1) NO `{ } | sqlite3` subshell pipe; (2) all statements in ONE `sqlite3 db "..."` argument, explicitly one after the other (not concatenated from a shell loop), with semicolons; (3) AFTERWARDS verify the effect with a count (waiting count before/after), do not rely on the 0 exit. Small (2-3 statement) calls work reliably; the big loop string is the risky one.
- **AND THE BROADER RULE THAT TWO SEPARATE CASES TAUGHT WITHIN AN HOUR (2026-08-16): A WRITE YOU
  ISSUED MUST NOT BE CONSIDERED DONE WITHOUT READING IT BACK -- REGARDLESS OF THE CHANNEL.**
  The point above is about the batch sqlite pattern. That day it came up in two FURTHER, independent forms,
  and neither was a batch:
  1. **KANBAN STATUS:** I issued an `UPDATE ... SET status='done'` for PR973; the title was rewritten, the
     assignee was rewritten, the STATUS was not. For 45 minutes the card stood with a title saying MERGED
     and a status of `waiting`. The sweep caught it, not me.
  2. **MEMORY API:** the `curl -X POST /api/memories` gave EMPTY output, I moved on, and the row
     was NOT created. It came out on reading back from the DB; resent, HTTP=200, id present.
  **THE COMMON CORE:** in both cases the command RAN, there was no error message, and my next step
  assumed success. The only difference is that one was found by a later round, the other
  by me, because I happened to look at it BY CHANCE.
  **PROCEDURE, two cheap habits:** (a) for a state-changing call (`UPDATE`, memory POST, message POST,
  file write) ALWAYS ask for the proof in the same round -- `curl -w "HTTP=%{http_code}"`, a
  `SELECT` after the insert, or reading the file back; (b) if the output is EMPTY where you
  expected a response, that is NOT success but an UNMEASURED state. Empty output is the most common silent error form,
  because nothing draws attention to it.
  **AND IN THE REPORT TOO:** do not write "saved" or "set", if you did not read it back --
  a false done report standing in the transcript does more harm than the missing write, because it removes
  the suspicion as well. Related: [[feedback_save_confirmation_must_reread_server_state]].

- **BEFORE A NEW CARD, FIND THE EXISTING ONE -- this applies to your own finding too (2026-08-01, HBWARNSTALE801, own error)**: I measured that the heartbeat warning line had been letter for letter the same over 14 consecutive rounds, opened a card for it, and prescribed a "measure-first" fix direction to the developer. Meanwhile HBWARN801 had been describing the same thing **since 10:16 that morning -- I had added it myself --**, and the fix was already merged (#832, fdab871), only waiting for deploy. The pair of the first pitfall above, only the other way round: there I believed an existing card was alive, here I did not even look for an existing card. PROCEDURE before a new card: `sqlite3 store/claudeclaw.db "SELECT id,status,substr(title,1,80) FROM kanban_cards WHERE archived_at IS NULL AND lower(title) LIKE '%<kulcsszó>%'"` -- grep for the keyword of the PHENOMENON (e.g. `heartbeat`, `warning`), NOT for your own wording, because the existing card almost certainly describes the same thing in other words (see `feedback_search_the_concept_not_the_sentence`). If there is a hit: your measurement goes as a COMMENT on the existing card (valuable, because it proves the fix is ineffective), and close and archive the duplicate with a stated reason.
